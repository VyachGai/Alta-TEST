# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page Russian-language web app for customs declarants ("Заполнитель" helper, Альта-Софт), with three tabs (`tabs.js` switches between them, storing the active tab in `sessionStorage`):

1. **Таблица товаров** (`app.js` + `ai-recognize.js`) — the user uploads commercial documents (invoice, packing list, specification) and the app merges them into one 27-column item table ready to import into the "Заполнитель" program.
2. **Проверка ограничений 311·312·313** (`checker.js`) — cross-checks ТН ВЭД codes against the item lists of Russian government resolutions 311/312/313, which the user supplies as consolidated RTF files (from a legal-reference system export); parsed lists are cached in `localStorage` so they survive a reload. Entirely independent of tab 1's code — it only reuses the SheetJS (`XLSX`) global directly to read the item table (XLSX/XLS/CSV, must have a ТН ВЭД column) and produces its own XLSX export via ExcelJS. Ported from the sibling repo `zapolnitel-app`; see that repo's README for the full spec of the matching logic (prefix match on digits-only codes, exclusions, "проверить" cases, etc.) if extending this block.

3. **Маркировка «Честный знак»** (`chestny-znak.js`) — checks the same kind of item table against the consolidated list of goods requiring identification marking ("Сводный перечень товаров, подлежащих маркировке средствами идентификации", an RTF export from a legal-reference system) and returns the operator's file untouched except for one appended column, «Честный знак» (`требуется` / `проверьте вручную` / `не требуется`). Independent of both other tabs; the parsed list is cached in `localStorage` (~230 KB) like tab 2's.

All document parsing happens client-side in the browser — files are never uploaded anywhere except when the optional AI-recognition feature (tab 1 only) sends document content to Claude via the app's own proxy server.

There is no build step, no bundler, no test suite, and no linter — this is plain HTML/CSS/JS loading libraries from CDN.

`app.js.bak` in the repo root is a stale snapshot, not loaded by `index.html` — ignore it and don't confuse it with `app.js` when searching/grepping.

## Commands

- Run the app with the AI-recognition proxy: `npm start` (runs `node server.js`, serves static files + `/api/anthropic` on `PORT`, default 3000). Requires `ANTHROPIC_API_KEY` in the environment; optional `ANTHROPIC_MODEL` (default `claude-sonnet-4-5`) and `PROXY_SECRET`.
- Run the app without AI (pure local heuristics, no server needed): open `index.html` directly in a browser. Internet access is still needed to load the CDN libraries.
- No test/lint/build commands exist. To verify a change, load the app (via `npm start` or `index.html`) and upload `examples/invoice_primer.xlsx` + `examples/packing_list_primer.xlsx` — see "Проверка работы" in README.md for the expected merged result (duplicate "Фильтр масляный" rows merged, place №1 gross weight split proportionally by net weight, "Прокладка резиновая" flagged yellow for a qty mismatch between the two files).
- Tabs 2 and 3 can be exercised without a browser: `npm i jsdom` in a scratch directory, load `index.html` with `runScripts: 'outside-only'`, wait for the `load` event **before** `window.eval`-ing the tab's script (its `init` runs on `DOMContentLoaded`, which has already fired), inject `window.XLSX`/`window.ExcelJS` from `node_modules`, and fire a `drop` event with a hand-made `{ dataTransfer: { files: [file] } }`. jsdom's `FileReader` hands back an `ArrayBuffer` from another realm that JSZip (inside ExcelJS) rejects — replace `window.FileReader` with one that returns a Node-realm buffer, otherwise the export silently fails with "Can't read the data of 'the loaded zip file'".

## Architecture

**`index.html`** — static shell. Loads CDN libs in order (SheetJS/`xlsx`, ExcelJS, pdf.js, mammoth.js), then `app.js`, `ai-recognize.js`, `checker.js`, `chestny-znak.js`, `tabs.js`. The `<thead>` column list and the `graph-strip` in the header are the canonical 27-column schema — keep them in sync with `renderResult()`/export logic in `app.js` if columns change. Four places must move together when a column is added: the two `index.html` lists, the `<tr>` template plus `<tfoot>` colspan/cell offsets in `renderResult()`, and `ws.columns` plus the hardcoded total-row cell indices and `SUM()` column letters at the end of the export handler.

**`server.js`** — thin Express app: serves the static files and exposes one endpoint, `POST /api/anthropic`, which injects `ANTHROPIC_API_KEY` server-side and forwards to `https://api.anthropic.com/v1/messages`. This is the only piece of backend in the project; it exists solely so the Anthropic API key never reaches the browser. Deployed on Railway per README.md; GitHub Pages deployment (see README) serves the static files only, so AI recognition is unavailable there (local heuristic parsing still works).

**`app.js`** (~2300 lines) — the whole client-side pipeline, in order:
1. Static classifiers/heuristics: `OKEI` (unit-of-measure regex table → ОКЕИ numeric/letter codes), `COUNTRIES` (ISO 3166-1), `KNOWN_BRANDS`, `parseNameParts` (splits a product name into brand/model/clean name), `FIELD_PATTERNS`/`detectField` (header-text → field-name matching).
2. File readers, dispatched by extension from `readFileItems`: `readSpreadsheet` (xlsx/xls/csv via SheetJS), `readPdf` (pdf.js; if a PDF has no text layer it's treated as a scan and throws a `SCAN:`-prefixed error that the UI renders as a special OCR instructions panel), `readDocx` (mammoth.js), `readTxt`.
3. Extraction over raw rows/text: `extractFromGrid`, `extractFromPdfPages`, `extractFromText` — locate the header row, map columns to fields, filter out totals/junk rows (`isTotalsRow`, `isJunkRow`, `isDocTrailerStart`). `extractFromGrid` ends by calling `mergeTranslations`, which handles the common Russian-invoice layout where **each item occupies two rows — Russian, then its Latin translation, with identical qty/price/total** (see `examples/`-style files such as a Новомет счёт-фактура): the Latin row is absorbed into the Cyrillic one, its name kept as `nameForeign` and the Cyrillic name set as `nameRu`. Both name fields must be set together — `ensureNameLangs` only splits items where *both* are empty, so filling one alone silently blanks the other column.
4. Cross-file assembly (triggered from the `build-btn` click handler): `mergeItems` groups items across all uploaded files and sums qty/total/weights for duplicates. Identity is article first, then **name + model + unit price** — invoices for electronics name every line the same («Mobile phone») and only the Model column tells goods apart, and one model shipped at two prices stays two rows so that `price × qty = total` holds. The grouping passes run in that order of trust: article → priced items without an article (which still join an article group when the name matches, since one document may leave the article column empty) → unpriced items (packing-list lines). Data from different files is never summed — a document set describes one shipment from several sides — so distinct batches must separate at grouping time, and the fuzzy name-similarity merge is blocked from re-joining groups that differ in model or (within one document kind) in price; without that block a whole batch silently vanishes, since the merged row takes the max, not the sum. Row order comes from the invoice — `docKind` classifies each file (invoice / spec / packing / other) by filename first and by which columns it carries otherwise, `sourceRank` maps that to 0/1/2, and each group is ordered by the best `{rank, file, seq}` among its parts, so the upload order never matters and goods absent from the invoice land after it. Every later group-merging step (`~byArt~`, `~byArticle~`, `~fuzzy~`) must carry the minimum order of the merged keys over to the new key, and the row loop re-sorts by it — a `Map` puts a re-keyed group at the end otherwise; `distributeGross` splits a packing place's gross weight across its items proportional to net weight (remainder assigned to the last item, 3-decimal rounding) — this is the core business rule described in README.md. `attachPackingWeights` runs right after it and handles the case merging cannot: a packing list lists one row per model («MAXVI C27i», 40 000 pcs) while the invoices split that model by colour and price, and the names have nothing in common, so the weight-only row is matched to the priced rows **by model** (`modelWords` drops the leading brand, `wordsPrefixMatch` allows the invoice's trailing colour) and its net/gross is spread across them proportional to qty; the match is accepted only when their qty sums to exactly the packing-list qty, which is what proves the whole set of one model was found. `buildRowByRow` is the alternate "one row per packing-list line" mode, pulling price by article from invoice files.
5. `resolveNameLanguages` (called from the `build-btn` handler between assembly and `applyMathErrors`) fills the two name columns. Items get `nameRu`/`nameForeign` from the AI path, or from `splitNameLanguages` — an alphabet heuristic that splits a bilingual name on a strong separator (newline, `|`, `;`, spaced slash, 3+ spaces) or a trailing parenthetical, falling back to a bare slash; a Latin brand/standard inside a Cyrillic name (`Подшипник SKF 6205`, `Болт М8х40 / DIN 933`) deliberately stays one Russian name. `ensureNameLangs` runs over items *before* merging, so a Russian name in one file and a foreign name in another land in one row without translation. Rows still missing `nameRu` are batch-translated by `translateNamesToRussian` through the proxy; every machine-translated row gets the `MT_WARNING` remark and a yellow flag. Without the proxy the column stays empty and a `state.notes` entry explains why.
6. `applyMathErrors` cross-checks computed totals against footer/document totals and flags mismatches; `renderResult` builds the on-screen table (with note/highlight styling) and the XLSX export path uses ExcelJS to reproduce fills and cell comments for the same mismatches.

**AI recognition has two independent, overlapping layers — know both when debugging "AI didn't recognize this file":**
- `ai-recognize.js` loads after `app.js` and **monkey-patches `window.readFileItems`**: for each file it sends the document (text, or rendered page images for scanned PDFs) to Claude through the `/api/anthropic` proxy with a strict JSON-array schema prompt, and only falls back to the original `app.js` local-heuristic `readFileItems` on any failure (network error, bad JSON, proxy down). This is the AI path that actually works end-to-end. **Text documents are sent in `CHUNK_CHARS`-sized pieces** (`splitDocText`/`chunkPrompt`): the reply is a JSON object per document row and so runs several times longer than the document itself, and a document that overflows `MAX_OUT_TOKENS` used to come back as JSON truncated mid-string — surfacing only as a cryptic `Unterminated string in JSON` note and a silent fall back to the local parser. Chunks are cut on line boundaries, every chunk after the first repeats the document head as column context, and `callClaude` treats `stop_reason === "max_tokens"` as an explicit error. Because a chunk boundary can fall between the two rows of a bilingual pair, `aiExtract` runs `app.js`'s `mergeTranslations` over the concatenated result whenever there was more than one chunk. The schema (`SCHEMA_INSTRUCTION`) also asks Claude to split the name into `nameRu`/`nameForeign` (translating into `nameRu` and setting `nameTranslated` when the document is foreign-only — this is the path that normally produces the Russian column, `app.js`'s `translateNamesToRussian` being the fallback for locally parsed files), and to extract `brand`/`model`/`maker` — from a dedicated document column if present, otherwise inferred from the item name/description — and `toItem()`/`fillBrandModelFallback()` map them onto the item; if Claude leaves brand/model blank, `fillBrandModelFallback` falls back to `app.js`'s `parseNameParts` heuristic on the name (relies on `parseNameParts` being a real global, since neither script uses an IIFE).
- `app.js` itself also contains AI helpers (`_callClaude`, `aiDetectFields`, `aiParseNames`, used inside `readSpreadsheet`/`readPdf`/`extractFromText`) that call `https://api.anthropic.com/v1/messages` **directly from the browser with no API key**. These always fail and are always caught, silently falling back to the local heuristic parsers (`parseNameParts`, `detectField`) — treat them as effectively dead/vestigial rather than a working AI path. `askClaude` (bottom of `app.js`) goes through the proxy correctly but is not called from anywhere.

**`chestny-znak.js`** — tab 3, self-contained like `checker.js` (own IIFE, own `chz-*` element ids, own `localStorage` key `zapolnitel.chestnyznak.v1`, exports `window.MarkirovkaChestnyZnak` for debugging). Pipeline:
1. `rtfVStroki` turns the RTF into **rows of cells** (`\cell` → cell, `\row` → row, `\par` → newline inside a cell). This is why it doesn't reuse `checker.js`'s `rtfVTekst`: the сводный перечень is one big table whose ТН ВЭД codes sit in one column and ОКПД 2 codes — visually identical digits — in the next, so flattening to plain text mixes them up.
2. `razobratPerechen` maps those rows onto the fixed layout `№ · наименование · ТН ВЭД · ОКПД 2 · срок · примечание · НПА`. A numbered row opens a position; an unnumbered row with codes continues it — such a row **names its own goods** («смартфоны» inside position 81 «Радиоэлектронная продукция») but usually leaves срок/примечание/НПА empty, so those three are inherited from the parent row while the name is not. Everything after the section header «Эксперименты, проводимые по маркировке отдельных товаров» is voluntary marking (it is also the yellow-filled part of the document) and never produces «требуется».
3. `razborGrafyKodov` reads the codes column, which is not just a list of codes: `(кроме 2009 11)` is an exclusion by code, `из 2309` and `(в части сушеной продукции)` mean the position covers only part of the code, `(за исключением товаров, указанных в …)` is an exclusion in words, and `2206 00 590 9 - код исключен с 04.02.2025` drops that code. A bracket may open on one line and close on the next, so depth is tracked across newlines.
4. `razborSroka` picks the date marked «(начало обязательной маркировки)» when the cell has several dates, otherwise the earliest. Note that JS `\b` does not see Cyrillic — `/\bпо\s+\d/` never matches «по 31 марта 2024», which is what breaks period detection for experiments.
5. `proveritTovar` decides by ТН ВЭД prefix only. `требуется` needs a match against a non-experimental position whose date has arrived and which carries no caveat; a future date, a worded exclusion, a partial-coverage marker or a товар code shorter than the list's code all yield `проверьте вручную`; experiments only ever appear as a parenthetical note on `не требуется`. The перечень's «Примечание» is copied into the cell after the word «требуется» — that text is what usually takes the goods back out of scope, so it must not be truncated.
6. Export: for `.xlsx` the operator's own workbook is reopened with ExcelJS and one column is appended (all sheets, styles and rows survive; ExcelJS does rewrite the sheet `dimension`, so SheetJS may then report the first column as starting one to the right — the cells themselves are unchanged). `.xls`/`.csv` cannot be reopened by ExcelJS, so the book is rebuilt from the values read by SheetJS.

## Data model

Parsed items carry: `source` (originating file name), `name` (the working name used for merging/consensus — never rendered), `nameRu`/`nameForeign`/`nameTranslated` (the two rendered name columns), `article`, `unitRaw`/derived ОКЕИ `num`/`let` codes, `qty`, `price`, `total`, `netUnit`, `netTotal`, `gross`, `place`, plus `brand`/`model`/`country`/`maker`/`tnved` where detected, and `mathErrors[]`. Rows in the final table also carry `grossParts`/`netParts` (per-place breakdown, consumed by `distributeGross`) before being flattened for rendering/export.
